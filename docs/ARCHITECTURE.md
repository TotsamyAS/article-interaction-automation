# Архитектура стенда

Источник требований — [article_project.docx](article_project.docx), разделы 4–5. Дополнение пользователя: отдельный шлюз сбора аналитики с экспортом CSV и Excel. Термины — [CONTEXT.md](../CONTEXT.md).

## Границы реализации

Реализованы backend и основной frontend для M1/M2/M3. Frontend использует Bun + Svelte 5, работает на порту `3033` и проксирует backend под тем же browser-origin. Компоненты из `frontend/references` переиспользованы: `TagInput` для M2, `LiveSearchProgress` для состояния сессии, `ConfirmDialog` и `AppToast`; табличная логика `Corpus` адаптирована без его API и ролей. Детали — в [FRONTEND-NOTES.md](FRONTEND-NOTES.md). M1 имеет пошаговый preview и итоговую проверку; M2 — единый запуск структурированного запроса; M3 — текстовый запрос, интерпретируемый небольшой LLM в тот же `Query` и затем выполняемый общим engine.

M4–M5 присутствуют в научном расписании, но запуск возвращает `mode_unavailable`: подменять их формой M2/M3 нельзя. Агентный M5 по текущему решению пользователя не реализуется. Поэтому полная пятиблочная экспериментальная сессия пока невозможна. Участник входит по индивидуальному многоразовому приглашению; псевдоним связывает данные, но сам по себе не даёт доступа. Исследователь имеет отдельную роль для общей аналитики. Публичной регистрации и паролей нет; Compose публикует только frontend на `127.0.0.1:3033`, backend остаётся во внутренней Docker-сети.

## Технологии и запуск

Backend: Python 3.13, FastAPI/Pydantic, SQLite из стандартной библиотеки, Uvicorn; Openpyxl используется для Excel-выгрузки. Frontend: Bun + Svelte 5 + Vite. Pytest/HTTPX используются для backend/API-проверок; frontend проходит `svelte-check` и production build в Dockerfile. Автоматических UI-тестов нет. Backend-зависимости закреплены requirements/constraints; frontend использует точные версии прямых зависимостей в `package.json`.

SQLite выбран для одного экспериментального сервера с короткими операциями над 120 записями. WAL, отдельное соединение на транзакцию, `BEGIN IMMEDIATE`, уникальные ограничения и лимит ожидания защищают конкурентные записи и повторные запросы. Один процесс приложения; долгие вызовы внешних систем в транзакциях не выполняются. Для M3 перед сетевым вызовом фиксируется `m3_interpretations.status=pending`, транзакция закрывается, а результат/ошибка записываются новой короткой транзакцией. Сам исполнитель `Query` остаётся полностью локальным и детерминированным.

Один `compose.yaml`, один постоянный том `/data`, автоматические последовательные SQL-миграции. Уже применённые миграции проверяются по контрольной сумме. Неизменяемый dataset manifest содержит только параметры, влияющие на набор данных, расписание/метрики и эталоны; эксплуатационные настройки доступа и M3 туда не входят, поэтому обновление приложения не делает существующий том непригодным. M3 отдельно сохраняет requested/response model, prompt version/hash, temperature, provider/system fingerprint и запрещает смешивать новую модель/prompt/temperature с уже начатым M3-сбором. `backend/config.json` и `frontend/config.json` владеют несекретными настройками своих сервисов. Browser-origin — `http://localhost:3033`; frontend-прокси направляет `/api`, `/health`, `/docs`, `/openapi.json` на `backend:8000`. Секреты `INVITATION_SIGNING_KEY` и `OPENROUTER_API_KEY` берутся только из корневого `.env`, который создаёт и заполняет пользователь; значения не дублируются в JSON, образе или исходниках. Несекретные `llm_base_url`, `llm_model`, `llm_temperature`, `llm_timeout_seconds` принадлежат `backend/config.json`.

## Доступ по приглашениям

`backend/scripts/invite.sh` запускается пользователем внутри контейнера и создаёт/повторно выдаёт ссылку для кода участника либо исследователя. В БД хранится только principal (UUID, код, роль, поколение, признак активности); сама ссылка подписана HMAC и не сохраняется. Повторный переход по действующей ссылке выдаёт новую HttpOnly-cookie с ограниченным сроком, поэтому участник может закрыть браузер и позже восстановить тот же прогресс. Отзыв увеличивает поколение и отключает principal, не удаляя экспериментальные данные.

Backend проверяет владельца сессии, пробы и попытки до чтения/записи ресурса. Для чужого ресурса участник получает `404`, чтобы не раскрывать существование идентификатора. Общая аналитика и каталог задач разрешены только роли `researcher`; участник получает через `/api/me` только собственные сессии. Изменяющие запросы дополнительно отклоняют явно cross-origin запросы. Frontend и API работают для браузера на одном origin `:3033`; `/health` и оболочка `/docs` остаются публичными, но защищённые `/api/*` данные требуют действующей cookie.

`public_base_url` задаёт ожидаемый browser-origin и схему cookie. Локально это `http://localhost:3033`; внешний адрес обязан быть HTTPS. Ссылка приглашения считается credential и не должна попадать в общие логи.

## Ручной M2-ввод

`GET /api/manual-query` возвращает согласованные placeholder, инструкцию и допустимые подсказки. `POST /api/manual-query/compile` принимает список строковых тегов и компилирует их в тот же контракт `Query`, который используют остальные детерминированные режимы. Поддерживаются фильтры, альтернативы через `/`, относительный период, агрегат, группировка, экстремум, сортировка и CSV-экспорт. Значения перечислимых полей сверяются с фактическим набором данных; даты и числовые сравнения проходят через общий исполнитель. Неизвестный/неоднозначный ввод возвращает ошибку, а не угадывается.

Ответ справки содержит типизированные `builders`: поля/действия, операторы, значения, placeholder и правила допустимости альтернатив. Этот словарь строится на backend из существующей грамматики и набора данных. Frontend показывает поле и значение связанными отдельными элементами, сохраняет явные строковые теги для общего компилятора. «И» соединяет условия; «ИЛИ» внутри одного положительного условия сериализуется через `/` в `in`. Несколько исключённых значений обозначаются «И НЕ» и компилируются в `not_in`. Незавершённый ввод блокирует кнопку выполнения.

Регрессионный тест строит через теги результаты всех C1a–C3e и сравнивает множества ID, агрегаты, выбранные группы и формат экспорта с каноническими задачами.

С 23.09 M2 сохраняет один DOM input для поля, значения, связок и действий. Enter/Tab завершает часть, но не закрывает возможность продолжить условие через «ИЛИ». `manual-input.ts` сериализует явный пользовательский синтаксис «И/ИЛИ/И НЕ» в прежние строковые теги, а бизнес-валидация и исполнение остаются на backend. Скобки и OR между разными полями явно отклоняются. Группировка записей — операция `Группировка: эпик`, а не логические скобки.

## Воспроизводимость

D0, seed и версия набора задаются в JSON. Данные, эталоны, контрольные суммы данных/каталога и параметры протокола сохраняются при первом запуске. Изменение протокола при существующем томе приводит к явной ошибке, а не к пересчёту результатов старых участников. Для нового эксперимента нужен отдельный том/Compose project name; старый том сохраняется.

Эталоны вычисляются до начала сессий. Проверки каталога независимо от общего исполнителя задают условия всех 15 задач и сравнивают ID и агрегаты. Указанный в статье TCI хранится как метаданные; приложение не пересчитывает научный индекс автоматически.

## Семантика обработки

- Все фильтры по умолчанию соединены AND. `in` выражает альтернативные значения одного поля. Явный OR разрешён только для соседних `eq` одного поля; другие сочетания возвращают ошибку `ambiguous_logic`.
- Проверки порядка доступны для дат и оценки. `eq/in` для меток означают членство/непустое пересечение; `neq/not_in` — отсутствие. Сравнения обычных значений с null дают false; для отсутствующих значений есть отдельные операторы.
- Даты — календарные UTC-даты. Последние N дней включают обе границы; просроченный дедлайн строго меньше D0.
- `grouping.field=null` с агрегатом выполняет агрегацию всей выборки. COUNT/SUM пустой выборки дают 0; AVG/MIN/MAX — null.
- `aggregation_field` для числовых агрегатов — `estimate_hours`; `extremum.metric` обязан совпадать с агрегатом. При одинаковом максимуме выбираются все группы.
- C3c исключает отсутствующего исполнителя: задача требует выбрать конкретного исполнителя, как предусмотрено §5.4.
- Для C3 проверяется множество отфильтрованных записей победивших групп и общее экстремальное значение. Для C1 агрегат игнорируется; для AVG применяется абсолютная погрешность ≤0,01.
- Экспорт в этом backend означает реальное создание и сохранение CSV результата с доступным endpoint скачивания. Клиент не передаёт флаг «экспорт выполнен». Для C3 CSV должен содержать записи, не только агрегат. Сохранение файла пользователем на локальный диск сервер подтвердить не может.

## Жизненный цикл и время

`pending → active → correct | incomplete`. Начало идемпотентно; завершённая проба не переоткрывается. Сервер проверяет порядок проб, обязательного ожидания между блоками нет (`break_seconds=0`, решение пользователя 22.09.2026). Таймер стартует при серверном подтверждении `/start`; UI показывает задачу после ответа.

Миграция `005_remove_mandatory_break.sql` обновляет только правило ожидания в сохранённом протоколе и записывает прежнее значение/время перехода в `protocol_changes`. Прогресс и исходные измерения не меняются. История попадает в `manifest.protocol_changes` сессии и научных выгрузок. Это явно согласованное исключение из запрета изменения сохранённого протокола; остальные проверки совместимости набора и эталонов сохраняются.

Пятая попытка может быть успешной. После пятого неуспеха проба закрывается; `Nretry_actual = max(attempts − 1, 0)`. При истечении времени новые попытки отклоняются. Успех принимается, если верификация завершилась строго до deadline; поздний результат не меняет итог. Таймаут материализуется при следующем обращении/экспорте, с временем окончания ровно deadline.

Фактический Tcorrect незавершённой пробы отсутствует; отдельные аналитические поля получают 300000 мс, A1=0, Nretry=4. Отсутствие первой попытки обозначается `A1_actual=null`. Времена сервера — UTC epoch milliseconds; Texec измеряется монотонным таймером. NTP на сервере относится к эксплуатационной настройке, приложение не настраивает часы ОС.

`request_id` однозначно связывает пробу и отправленное содержимое. Повтор возвращает сохранённый ответ без новой попытки; другое содержимое с тем же ID вызывает конфликт. UUID здесь идентификаторы, не секреты и не токены доступа.

События передаются пакетами по 500, имеют `event_id`, возрастающую `sequence` и неубывающий `offset_ms` относительно начала пробы. Frontend журналирует ввод, фокус, навигацию и начало/конец системных запросов; активная проба получает с сервера `next_event_sequence` и `last_event_offset_ms`, поэтому после reload журнал продолжается без сброса sequence. Повтор пакета не удваивает события. События допускается доставить после завершения, если их время попадает внутрь пробы. Клиент пытается доставить очередь при смене/завершении пробы; перед финальной научной выгрузкой следует завершить активную работу участника. Последовательные активные интервалы с разрывом ≤5 с складываются; паузы больше 5 с исключаются целиком. Объединение интервалов ожидания и потери фокуса вычитается один раз.

`elapsed_since_start_ms` сообщает текущую серверную длительность даже активной пробы (фактическая итоговая метрика `elapsed_ms` по-прежнему заполняется только после завершения). От неё frontend продолжает отсчёт через `performance.now()`, без сравнения часов ОС с сервером. На время отправки попытки события буферизуются; после терминального ответа события позже серверной границы исключаются, остальные отправляются. Ошибки последовательности, порядка времени и выхода за границу пробы имеют разные коды и понятные сообщения. Сбой журнала выводится отдельным предупреждением и не превращает сохранённую успешную попытку в ошибку отправки.

## M3: LLM только как компилятор текста в Query

M3 не получает отдельного вычислителя. Endpoint `/api/trials/{trial_id}/m3-attempts` принимает `request_id` и текст участника, вызывает `OpenAICompatibleInterpreter`, валидирует structured output через тот же Pydantic `Query` и передаёт его существующему `ExperimentService.submit`. Фильтрация, агрегаты, группировка, экстремум, CSV и сравнение с эталоном выполняются тем же кодом, что для M1/M2. Поэтому валидность JSON и правильность результата измеряются отдельно.

Prompt оптимизирован под маленькую модель: в нём нет общего «поговори с пользователем», а есть роль компилятора, фактические категориальные значения набора, фиксированная D0, канонические правила для `in`, относительных дат, NULL, labels, COUNT/SUM/AVG, группировки/экстремума/экспорта и несколько синтетических few-shot примеров. Экспериментальные тексты C1a–C3e и их эталонные ответы в prompt не включаются. Strict JSON Schema строится из `Query.model_json_schema()`, дополнительно запрещает неизвестные поля и требует все свойства.

Конфигурация по умолчанию: OpenRouter `https://openrouter.ai/api/v1`, `openai/gpt-4.1-nano`, `temperature=0`, `seed=0` в запросе. OpenRouter получает `require_parameters=true`, чтобы structured-output параметры не были молча отброшены. Включена routing metadata; журнал сохраняет фактическую модель, provider и `system_fingerprint`. Prompt имеет собственную версию и SHA-256 в protocol manifest, поэтому изменение prompt/LLM-настроек требует нового экспериментального тома так же, как изменение набора данных.

`m3_interpretations` хранит текст, raw response, валидированный Query, модель/provider/fingerprint, `Tllm`, token usage и класс ошибки. Ошибка сети/провайдера, невалидный structured output или структурно несовместимый Query не создают `attempt`; валидный и исполнимый Query всегда проходит полный executor и уже затем считается корректным/некорректным как обычная попытка. Идемпотентность `request_id` не вызывает LLM повторно при сетевом повторе известного запроса.

## Аналитика для статьи

Отдельной панели аналитики в frontend не будет: исследователь анализирует выгрузку Excel. Endpoints аналитики защищены ролью `researcher`; CSV/Excel и описательные сводки в файлах сохраняются.

Шлюз `/api/analytics` использует ту же функцию расчёта метрик, что карточка пробы. Экспорт ZIP/XLSX формируется из одного транзакционного снимка; исходные события и попытки остаются доступны для независимого пересчёта.

- `trials`: одна строка на пробу, связи с участником/сессией/режимом/сложностью, статус, фактические и штрафные показатели.
- `attempts`: одна строка на попытку, её запрос, результат, корректность, серверные времена и Texec.
- `events`: низкоуровневые действия и клиентские интервалы с временем получения сервером.
- `summary`: описательная сводка по kind × mode × level. В расчёт средних входят только завершившиеся пробы; фактическое среднее Tcorrect — только успешные. Знаменатели и количество незавершённых указываются отдельно, пустое среднее — null.
- `protocol`: версия схемы экспорта, настройки, контрольные суммы, время снимка и фильтры.

Тренировки исключены по умолчанию; при явном включении группируются отдельно. Единицы всех временных показателей — миллисекунды. CSV — UTF-8 с BOM, разделитель запятая. Excel содержит шесть листов (`protocol`, `trials`, `attempts`, `events`, `interpretations`, `summary`). ZIP содержит пять CSV и `protocol.json`. Формул в ячейках из пользовательских данных не создаётся; длинные значения сверх лимита Excel отклоняются с предложением CSV/ZIP, а не обрезаются.

Статистические тесты, графики и выводы статьи в это приращение не входят. Сохраняются исходные данные для их последующего воспроизводимого анализа.
