# Frontend

## Указания пользователя

- Frontend использует Bun. Предоставленные компоненты используют синтаксис Svelte 5.
- Отдельная панель аналитики не требуется: исследователь работает с выгрузкой Excel. Backend-экспорт CSV/Excel сохраняется.
- Компоненты получены в `frontend/references`; исходники сохраняются как примеры для адаптации.
- M2 — ручной TagInput с минимумом полей: выбор подсказок и ручной ввод структурированных условий равноправны. Решение принято пользователем; правка статьи отложена, реализацию можно продолжать.
- За основу отображения прогресса берётся `LiveSearchProgress.svelte`.

## Реализованное состояние

Frontend собран на Bun + Svelte 5 и доступен на `http://localhost:3033`. Browser-origin единый: production server проксирует `/api`, `/health`, `/docs` и `/openapi.json` на backend внутри Docker. Благодаря этому invitation cookie и backend same-origin policy работают без CORS-обходов.

Переиспользование выполнено до написания основных экранов:

- `TagInput.svelte` адаптирован в `src/lib/components/TagInput.svelte`: сохранены chips, подсказки и клавиатурная навигация; добавлено редактирование тега кликом. Enter/Tab подтверждают ввод; Tab на пустой строке без выбранной подсказки сохраняет обычную навигацию.
- `LiveSearchProgress.svelte` адаптирован для прогресса сессии и состояния запросов без выдуманного процента системной операции.
- `ConfirmDialog.svelte` используется для выхода.
- `AppToast.svelte` используется для результата попытки; отсутствующий portal старого проекта удалён.
- `Corpus.svelte` не переносился целиком: переиспользована только идея табличного представления, реализован независимый `ResultsTable` под текущие API-контракты.

M1 и M2 используют один backend `Query`/executor. UI не содержит эталонных решений. M1 выполняет preview отдельно от попытки; M2 компилирует выбранные/введённые теги через `/api/manual-query/compile` и создаёт попытку только по нажатию «Выполнить».

Task Mining реализован отдельным `TrialEventLogger`: ввод, pointermove/scroll с throttling, focus, navigation, системные request start/finish. При восстановлении активной пробы frontend продолжает `sequence` и `offset_ms` из серверных `next_event_sequence`/`last_event_offset_ms`.

## M2: согласованный принцип ввода

Один компактный конструктор: пользователь добавляет только нужные условия в виде редактируемых тегов. Сначала выбирает поле, затем оператор и допустимое значение. Дополнительные операции (агрегат, группировка, экстремум, экспорт) добавляются по необходимости. Один запуск «Выполнить» исполняет собранный запрос.

Пример представления C2a:

`([Эпик] [Платежи]) И ([Статус] [В работе] ИЛИ [На ревью]) И ([Период] [14 дней]) · ДЕЙСТВИЕ ([Итог] [количество])` → «Выполнить». Скобки здесь обозначают визуальную группу связанных элементов, а не произвольный язык выражений.

Подсказки показывают допустимые поля, операции и значения, но не подставляют решение из предъявленной задачи. Пользователь вручную задаёт каждое условие; свободный текст задачи не интерпретируется автоматически. Это сохраняет отличие M2 от M3 и единый запуск M2 в отличие от пошагового M1.

Уточнение пользователя 23.09: один постоянный `<input>` на всех шагах. После Enter/Tab фокус остаётся в нём, а контекст последнего условия сохраняется. `Статус` → `В работе` → `ИЛИ` → `На ревью` строит одну группу; `И` начинает новое условие. Целиком введённое условие тоже поддерживается. Готовые теги можно редактировать, альтернативы дописывать через ту же строку или кнопку на нужной группе. Синий шаг — поле/действие, зелёный — значение, фиолетовый — связка; подписи доступны без различения цветов. Подсказки не ограничены первыми 12 пунктами: «Группировка», «Итог», «Экстремум», «Экспорт» доступны без отдельного экрана или переключателя. Под строкой постоянно показан пример группировки записей. Для отрицаний используется «И НЕ». Esc отменяет черновик; Tab на пустой строке сохраняет обычную навигацию. Скобки не означают группировку записей и не поддерживаются как логический синтаксис.

В M1 убрана зависимость ширины колонок от длинных значений `select`; кнопка удаления фильтра занимает фиксированную колонку справа, в том числе на узком экране. Поля операций имеют одинаковую высоту. Визуальная проверка пользователем после пересборки ещё нужна.

Журнал и таймер используют серверный `elapsed_since_start_ms` и `performance.now()`. После сохранённого ответа сбой отправки событий показывает отдельное предупреждение, а не ошибку ответа. Переход к следующей доступной пробе не требует обязательного перерыва; порядок проб и их собственный таймер сохранены.

Уточнение M2: `Статус` (без двоеточия и значения) выбирает поле. Единственная подходящая подсказка выделяется автоматически и принимается Enter/Tab. `НЕ` и `Исключить` открывают выбор исключаемого поля, затем значения. Тот же результат даёт `НЕ Приоритет: Низкий` либо `Приоритет: НЕ Низкий`. Группа помечена «Исключить»; её поле и значения редактируются как обычные теги. Компилятор backend по-прежнему получает каноническое `Приоритет != Низкий`. `И НЕ Средний` продолжает исключение того же поля, а `И НЕ Статус: Закрыта` создаёт другое отрицательное условие. Отрицание действий, дополнительного сравнения и двойное отрицание явно отклоняются.

## Доступ

Индивидуальные многоразовые приглашения создаются `backend/scripts/invite.sh` внутри Docker. Backend уже проверяет cookie и владельца сессий/проб/попыток; повторный вход возвращает того же участника с его прогрессом. Отсутствие ФИО/email не делает ссылку публичной: она даёт доступ к прогрессу. UI ввода имени и публичное создание чужих сессий не нужны. Frontend после загрузки вызывает `/api/me`; при `401` показывает только инструкцию открыть персональную ссылку, без формы регистрации.

## M3

M3 намеренно проще M2: одно многострочное поле естественного языка и кнопка «Выполнить». Frontend не показывает распознанный `Query`, не предлагает эталонные фразы и не исправляет смысл запроса локально — иначе измерялся бы ещё один интерфейсный помощник. После ответа используется тот же `ResultsTable`, что в M1/M2; CSV скачивается через существующий `export_url`.

Во время `/m3-attempts` `LiveSearchProgress` показывает системное ожидание «Интерпретируем запрос…», а Task Mining записывает парные `request_started/request_finished`; это время исключается из пользовательской активности тем же механизмом, что другие системные ожидания. Для неопределённого сетевого сбоя frontend повторяет тот же `request_id`; если сервер уже ответил ошибкой, следующая отправка создаёт новый `request_id` и новый LLM-вызов.
